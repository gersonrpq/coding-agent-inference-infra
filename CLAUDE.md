# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A K3s deployment that serves a coding agent (pi) from **one H100 PCIe 80 GB split by MIG into 2 × `3g.40gb`**: two SGLang workers behind a LiteLLM gateway, observed with Prometheus/Grafana. Model: `Qwen/Qwen3.5-9B`, bf16 weights and bf16 KV (no quantization anywhere, decision [17](ARCHITECTURE.md#decision-17)), 64K context, `MAX_NUM_SEQS=6` per worker (12 running in the fleet), HiCache GPU → host RAM → Mooncake L3 (`write_through`), radix eviction `lru`. The 2× H100 target is `Qwen/Qwen3.6-27B-FP8` (22 per worker, fleet 44); capacity numbers in the docs that say 22/44 are that target. The model and engine knobs live in ConfigMap `sglang-config`.

This is a course project (final project: design the cluster, write the control plane, prove it on a real GPU). `DESIGN.md` is the short, plain-language design for any reader; `ARCHITECTURE.md` is the full technical record (model choice, KV math, layers, admission, status codes, metrics, **Decision log**, **Roadmap**, **Glossary**). Source of truth for behaviour: the manifests in `cluster/` and the code in `control/`. Clients must go through LiteLLM, never SGLang directly.

## Workflow

Edit locally → `bash setup/sync_lambda.sh` → apply and test **in the real cluster over ssh** (`$LAMBDA`, `$LAMBDA_SSH_KEY` from `.env`, `KUBECONFIG=/etc/rancher/k3s/k3s.yaml`). The pure control-plane logic is covered by local unit tests; the engine, Mooncake and the LiteLLM integration only run in the cluster. No `.py` files under `cluster/` (helper scripts live in `monitoring/`).

Long jobs on the server: write `/tmp/x.sh`, `scp` it, `setsid nohup bash /tmp/x.sh > ~/x.log 2>&1 < /dev/null &`, poll the log with bounded waits. Never `pkill -f` over ssh (it kills itself); select the **newest Running** LiteLLM pod (`--field-selector=status.phase=Running --sort-by=.metadata.creationTimestamp`), not the first.

## Architecture (spans several files)

**The control plane runs inside the LiteLLM process as callbacks and libraries, not as a separate service, and it is deliberately small: `control/` has four modules (decision [55](ARCHITECTURE.md#decision-55)).** ConfigMap `litellm-security` is mounted at `/app/security` (`PYTHONPATH=/app/security`). `control/inspect.py` is renamed `security_inspect.py`; the others keep their names; code imports `security.fleet_state` / `security.place`, and `litellm/config.yaml` references `security_inspect.security_inspect` and `admission.admission_handler`. **A module must be imported under one name only** (importing it twice breaks the Prometheus registry); that is why shared state lives in modules imported as `security.*`. LiteLLM runs as **one replica and one process**: the placement counters and the in-flight semaphore are in memory, so scaling it out would multiply capacity. Changes to `control/` or `litellm/config.yaml` need the ConfigMap re-applied and LiteLLM restarted. Callback order: `prometheus` → `security_inspect` → `admission_handler`. Anything LiteLLM can do by configuration is configuration (the in-flight cap, tenants as virtual keys); code exists only for what it cannot express (the guard, the KV/batch checks, the batch share, `affload`).

**Request path:** client → LiteLLM (virtual key, **in-flight cap of 14**, context-window check, `num_retries: 0`) → `inspect.py` (guard: model alias, roles, tools, 4096 output cap (clamped, decision [54](ARCHITECTURE.md#decision-54)), priority class 1-10 (interactive values normalised to 5), no `n` > 1, content parts: text and `data:` images only (no remote URLs), fail-closed 503, default `priority=5`) → `admission.py` (stateless checks, batch share, placement call) → LiteLLM router → SGLang. The proxy reports chat calls as `acompletion`: hooks must accept `GUARDED_CALL_TYPES`/`GENERATION_CALL_TYPES`.

**Admission and the cap.** The queue allowance **K = 2** (decision [42](ARCHITECTURE.md#decision-42), measured): at most `12 + K = 14` requests are in flight, enforced by **LiteLLM's own admission middleware** (`max_in_flight_requests_per_worker: 14`, `max_queued_requests_per_worker: 0` in `litellm/config.yaml`; a semaphore, 503 `queue_full` at once; it counts every route except `/health*`, so `/metrics` can be refused when full). Nothing is held at the gateway; admitted requests wait in SGLang's priority queue. `admission.py` sheds (503, `source: admission`, header `shed-reason`): `kv_pressure` (new prefix at KV ≥ 95 %), `batch_pressure` (fleet TTFT p99 > 4× p50 **and > 10 s**, batch only; the floor is `BATCH_PRESSURE_MIN_P99_S`), `batch_share` (batch is admitted only while fewer than `BATCH_ADMIT_BELOW` = 10 requests of any class are in flight, so the last 4 places are for interactive calls), `timeout_queue` (estimate rule, **off by default**: it reads gauges that are stale by seconds). The decision is the pure function `should_shed(req, snap)` -> `(shed?, code, reason, retry_after)`; placement adds `no_healthy_worker` (503) when no worker answers its metrics. `ADMISSION_CHECKS` is an env switch. **There is no first-token cut** (tried and removed, decisions [59](ARCHITECTURE.md#decision-59) and [61](ARCHITECTURE.md#decision-61)): it was LiteLLM's `stream_timeout`, which is the socket read timeout of the whole stream, and SGLang's `qwen3_coder` parser is silent while a tool call's arguments are generated (68 s for a 300-line file), so with it pi could not write files. The TTFT bound comes from K = 2. After a failed call the **overflow gate** (`overflow_decision`, 8 lines) counts stay or leave: 429, 500, `slice_oom` and anything refused by the guard stay, capacity 503/529 may leave; forwarding is OFF (`OVERFLOW_ENABLED=0`, and the Superlinked endpoint answered 500/402: billing, wallet exhausted). `max_parallel_requests` (40 per worker) and `global_max_parallel_requests` (128) are only a safety net far above the cap (they answer 429, which never overflows). SGLang's `--max-queued-requests` is **not** used to bound the queue (it refuses bursts while slots are free and answers 500): leave `MAX_QUEUED_REQUESTS` unbounded.

**Tenants and keys.** LiteLLM runs with PostgreSQL (`cluster/postgres/`, `DATABASE_URL` from the Secret). Every client has its own virtual key with its own limits (`script/make_keys.py` creates `pi-demo`, `loadgen`, `tenant-acme`, `tenant-beta` and appends `LITELLM_KEY_*` to `.env`); the master key is for administration only. An over-limit key gets a 429 from LiteLLM. Never print `.env`.

**Placement** (`control/place.py`): `PLACEMENT_POLICY=affload` (default since decision [50](ARCHITECTURE.md#decision-50)) keeps a session on its previous worker unless that worker has `PLACEMENT_SLACK` (3) more requests in flight than the other; new sessions and batch go to the least loaded, equal loads broken by the engine queue depth (`sglang:num_queue_reqs`). `pick` returns a worker or a `Shed` (503 `no_healthy_worker` if no worker answers its metrics) and never picks a worker that is down; a worker that comes back is **ramped** (weight 0.25 -> 1 over `RAMP_SECONDS` = 60 s, the clock paused while the fleet TTFT p99 > `RAMP_HOLD_P99_S` = 10 s). The hook rewrites the model to the aliases `qwen-coding-w0/w1` (copies of the two local deployments in the LiteLLM config). `litellm` leaves the choice to `routing_strategy` (`least-busy`). Sessions are identified by the hash of the first user message. When it moves a session it records the hop (`orch_hops_total`, `orch_hop_tokens_total`): the move itself is done by SGLang's hierarchical cache. Compared in `notes/routing-experiment.md`.

**Priority convention:** lower number = more urgent; `<= 5` interactive, `> 5` batch. Workers run `--enable-priority-scheduling --schedule-low-priority-values-first --default-priority-value 5 --retraction-policy priority`; admission forwards the value as `extra_body.priority` (LiteLLM does not forward it on its own).

**Fleet state** (`control/fleet_state.py`): a poller (every 15 s) scrapes each URL in `SGLANG_REPLICA_URLS` into `global_fleet_state`. Totals of `num_queue_reqs`/`num_running_reqs` use only the `priority=""` series (SGLang adds a per-priority breakdown). TTFT quantiles use a 60 s window with at least 20 samples. SGLang's queue/running gauges change in steps every few seconds, so decisions on them are always late.

**Workers** (`cluster/sglang/`): two Deployments + Services (not replicas); `worker-0.yaml`/`worker-1.yaml` differ only in name, label, port (30000/30001) and `CUDA_VISIBLE_DEVICES` (0/1); keep them in sync. `hostNetwork: true` and `privileged: true` (Mooncake over RDMA/RoCE), so ports are distinct. Knobs from ConfigMap `sglang-config`: `MODEL_NAME`, `KV_CACHE_DTYPE`, `MAX_MODEL_LEN`, `MAX_NUM_SEQS`, `MAX_MEM_FRAC` (fraction of the 39.5 GiB instance), `MAMBA_FULL_MEMORY_RATIO` (0.17: share of the pool kept for the recurrent states of this hybrid model), `HICACHE_WRITE_POLICY` (`write_through`), `RADIX_EVICTION_POLICY` (`lru`), `CHUNKED_PREFILL_SIZE` (4096), `MAX_QUEUED_REQUESTS`. Prefill CUDA graphs are disabled (5.4 GB and 209 s per worker). Readiness/startup probes are `/health` with a 20 s timeout. Images are pinned by digest (sglang 0.5.21, litellm 1.105.0).

**Monitoring** (`cluster/monitoring/`): SGLang is one Prometheus job `sglang` with native names (`sglang:*`) and a `worker` label ("0"/"1"). LiteLLM and Mooncake metrics are renamed with a prefix (`litellm_*`, so LiteLLM's own are `litellm_litellm_*`; `mooncake_*`). Control-plane metrics are `litellm_orch_*` (fleet and overflow decisions in `fleet_state.py`, placement and hops in `place.py`; listed in ARCHITECTURE.md); the cap's own metrics are LiteLLM's `litellm_litellm_admission_*`. Spend is `litellm_litellm_spend_metric_total`, booked with the GPU-time rates in the LiteLLM config (provisional). Every dashboard panel has a DEFINITION / WHY IT MATTERS description and each dashboard starts with an About panel; keep that format. Prometheus storage is `emptyDir`: a restart loses history.

## Known oddities

- **Privileged workers see both MIG instances** and the NVIDIA runtime rewrites `NVIDIA_VISIBLE_DEVICES` to `void` for PID 1, so the manifests pin `CUDA_VISIBLE_DEVICES` per worker. Without it both land on instance 0 and the second OOMs. On a real 2× H100 node skip MIG.
- LiteLLM sends `openai/<MODEL_NAME>` upstream: keep `model:` in `litellm/config.yaml` equal to `MODEL_NAME`. The overflow model (`Qwen3.8-27B-FP8`) differs on purpose; `fallbacks` is commented out and, at router level, would only cover engine-side failures, not admission sheds.
- pi's global config (`~/.pi/agent`) defaults to the external API and asks for 16384 output tokens (the guard caps at 4096); `app/` carries its own config. The user does not want the Superlinked default touched.
- The hybrid model's prefix is reusable on the other worker only after its recurrent state has been published (it happens when evicted from the 46-state pool); KV is published immediately with `write_through`.
- `nvidia-smi` gives no GPU utilization under MIG (use power); `sglang:generation_tokens_total` is updated when a request finishes, not while it runs.
- Built: virtual keys on PostgreSQL, the warm gate (`script/warm_workers.py`), the ramp of a returning worker, four alert rules, the overflow gate (forwarding OFF). Out of scope by decision [62](ARCHITECTURE.md#decision-62): autoscaling/KEDA and a `stale_telemetry` shed (reported by alert only); the real overflow is blocked because the Superlinked wallet is exhausted (402 on 2026-10-03), so forwarding stays OFF. The final tests F1-F5 (`notes/final-load-tests.md`) ran with the old counter; the simplified control plane is re-checked by comparison runs (decision [57](ARCHITECTURE.md#decision-57)).
